# XGN-29: XGN Composed GET Capability and Replay Security

**Status:** Proposed | **Version:** 1.0 | **Date:** 27 November 2026
**Module ID:** XGN-29 | **Group:** C — Transport
**Owner:** Gitana Architecture
**Depends on:** XGN-01, XGN-02, XGN-03, XGN-10, XGN-24 | **Supersedes:** none
**Conformance:** XGN-26 | **Open decisions:** none outstanding at this level

**Normative language:** MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119.

## 1. Purpose and scope

This module defines the **command capability** for the Composed GET transport: its format, what it binds to, how the server validates it, its lifecycle, the exact-retry idempotency rule, the detection of theft and replay, the identity of the caller, the logging rules that apply to it, and revocation.

In scope: the capability value format and entropy; the binding tuple and its validation; issuance, consumption, rotation, supersession and expiry; the 90-second exact-retry window and what a retry must match; reuse detection and suspension; caller identity and the status of network fingerprints; query-string logging and redaction; and revocation.

Out of scope: the transport surface and the anti-prefetch protections (XGN-10), the command catalogue and the sequence number semantics (XGN-28), the session and grant model (XGN-04), the caller identity model as a whole (XGN-05), the general threat model and residual risk register (XGN-24), the gateway configuration (XGN-20), and the error catalogue (XGN-23).

## 2. Capability format

```text
cap_ + 22 base64url characters
```

| Property | Rule |
|---|---|
| Prefix | `cap_`. A value that does not match the format MUST be refused as `VALIDATION_FAILED`. |
| Suffix | 22 characters drawn from the base64url alphabet `A-Z a-z 0-9 - _`, with no padding. 22 characters encode 16 bytes, which is 128 bits of entropy. |
| Entropy | At least 128 bits, generated by a cryptographically secure random source (XGN-DEC-004). |
| Opacity | The value MUST NOT encode the session, the node, the sequence number, the grant, the permitted commands or any timestamp. It MUST be an opaque bearer value. |
| Non-reuse | A value MUST NOT be issued twice. A value MUST NOT be reused after revocation. |

**L-nn rationale.** The inherited material tested a 43-character token in the capability-length probe while recommending a 22-character token. That inconsistency is corrected here: **22 characters is the production format**, and the probe that exercises a capability of production length is XGN-30 PRB-08. A 43-character value is not a valid capability and MUST be refused.

**Why the value carries no binding.** If the value encoded which commands it permitted, anyone holding the value could read the binding off it. The binding therefore lives in the issuing component's registry, and the value is a random lookup key. This is also what makes the capability's exposure tolerable: an observer learns nothing from the value itself.

## 3. Capability binding

A capability is bound to the following tuple when it is issued. The binding is held in the capability registry; it is not recoverable from the value.

| Bound element | What it fixes |
|---|---|
| `session_id` | The session the capability acts in. |
| `grant_id` | The grant in force when the capability was issued. |
| `node` | The surface node the session is at, so that a command issued for one node cannot be carried into another. |
| `expected_next_seq` | The session sequence number the capability may carry. |
| `permitted_commands` | The command names the capability may carry, with the permitted parameter names for each. |
| `issued_at`, `expires_at` | The capability lifetime. |

The permitted command and parameter names are summarised in a `binding_digest`: the SHA-256 over the canonical serialisation of the tuple above, in the canonical form of XGN-08. The registry holds the digest so that a tampered registry entry is detectable, and so that the same capability description can be re-derived from it (XGN-03 CD-01).

**L-nn validation.** On every request that carries a capability, the trusted runtime MUST verify all of the following before any other processing:

| # | Check | Refusal |
|---|---|---|
| 1 | The value matches the format in section 2. | `VALIDATION_FAILED` |
| 2 | The value exists in the capability registry. | `LINK_UNKNOWN` |
| 3 | The registry entry is not expired. | `LINK_EXPIRED` |
| 4 | The entry is in state `issued`, or it is an exact retry of a consumed entry inside the idempotency window. | `LINK_CONSUMED` |
| 5 | The entry's `session_id` matches the session the request resolves to. | `LINK_UNKNOWN` |
| 6 | The presented `cmd` is in `permitted_commands`, and every presented parameter name is in the permitted parameter names for that command. | `VALIDATION_FAILED` |
| 7 | The presented `seq` equals `expected_next_seq`, unless the command is `status`. | `SEQ_INVALID` |
| 8 | The current node matches the bound `node`, except that a command that returns to an earlier node is permitted where the catalogue allows it. | `STATE_INVALID` |
| 9 | The recomputed `binding_digest` matches the stored digest. | `INTEGRITY_MISMATCH` |

**Resolving the inherited gap.** The inherited material asked how a token binds to the permitted command and parameter names when the agent supplies the values. The answer is that the binding is to the **names**, never to the values. The agent supplies values; the runtime checks the names against the bound sets and the values against the operation catalogue, the grant scope and the size limits. A capability therefore permits a command in principle; it never permits a value in advance.

## 4. Capability lifecycle

| Stage | Rule |
|---|---|
| Issued | A capability is issued by the runtime in every reply that follows an accepted command and in every reply that follows a refused command (INV-11). A capability base read returns the current capability and issues no new one (XGN-DEC-017). |
| Single use | A capability is consumed by the first complete valid command it carries. It MUST NOT carry a second command (INV-08). |
| Rotated | Every command reply issues a capability that has never been issued before. The presented capability is retired, whether the command was accepted or refused. |
| Superseded | A retired capability is kept in the registry in state `superseded` for the idempotency window, then removed. Presenting it later is a reuse. |
| Expired | A capability is valid until it is used or for 10 minutes, whichever comes first (XGN-DEC-008). An expired capability MUST NOT be honoured. |
| Revoked | Revocation invalidates every outstanding capability of the session immediately (section 9). |

**L-nn note.** The gateway MAY hold a short-lived copy of the registry for rate accounting and for rejecting malformed tokens early (XGN-00 section 5.1). That copy MUST NOT be authoritative. The trusted runtime holds the authoritative registry, and a disagreement is resolved in favour of the runtime (XGN-00 section 5.1, XGN-30 PRB-26).

## 5. Exact-retry idempotency

A lost reply is the normal failure mode of this transport: the command reached the server, the server acted, and the reply did not reach the agent. The agent must be able to retry without producing a second effect.

| Rule | Requirement |
|---|---|
| L-R1 | The exact-retry window is 90 seconds, measured from the moment the original command was accepted or refused (XGN-DEC-007). |
| L-R2 | A retry MUST be byte-identical: the same capability value, the same command name, the same parameter values, the same parameter order, and the same body digest. |
| L-R3 | A retry that satisfies L-R2 and arrives inside the window MUST return the cached reply byte for byte, including the capability that reply carried, and MUST produce no second effect (INV-08). |
| L-R4 | The cached reply MUST NOT be re-rendered. It MUST NOT contain a new capability, a new sequence number or an updated timestamp. |
| L-R5 | The cached reply MUST be stored by the trusted runtime, not by the gateway, because it may contain agent-written content (XGN-DEC-027). |
| L-R6 | After the window, a byte-identical retry MUST NOT be recoverable by the agent alone. The capability is already consumed, the retry MUST be refused as `LINK_CONSUMED` and MUST be recorded as a reuse. |
| L-R7 | After the window, the agent's recovery is to read authoritative state with `status`, which consumes nothing, and to have the operator issue a new session link. A transport retry MUST NOT be treated as permission to repeat a protected side effect (XGN-22). |

**Worked example.** The agent issues `append` on capability `cap_A` and the reply is lost. The agent re-sends the identical URL within 90 seconds. The runtime finds the cached reply for that exact request and returns it, together with the capability the lost reply carried. The draft has one part, not two, and the sequence number has advanced once, not twice.

**L-R8.** A retry that is not byte-identical is not a retry. Presenting a consumed capability with different content is a reuse, and is handled by section 6.

## 6. Theft and replay detection

| Rule | Requirement |
|---|---|
| L-T1 | Every presentation of a consumed or superseded capability MUST be recorded as a `LINK_REUSE` event, whether or not it succeeds. |
| L-T2 | The event MUST record the session, the capability registry entry, the command presented, whether the request matched the cached request byte for byte, the timestamps, and the request metadata. It MUST NOT record a capability value or agent content. |
| L-T3 | Unless the presentation is an exact retry inside the window from the same session, the session MUST be suspended and the operator MUST be alerted (INV-09). |
| L-T4 | A suspended session MUST NOT accept any further command. The operator reviews it and resumes or revokes it. The agent cannot lift the suspension. |
| L-T5 | When a legitimate agent and an attacker both use the same session, one of them presents a consumed capability. That presentation surfaces the fork. |

**L-T6 — what detection does and does not achieve.** This design **detects use; it does not prevent the first use by an attacker.** An attacker who holds a live capability and uses it first, inside its 10-minute lifetime, produces a valid transition that the runtime cannot distinguish from the legitimate agent's. What bounds that outcome is the rest of the framework, not this module:

| Control | What it bounds |
|---|---|
| Short capability lifetime (10 minutes) | The window in which a stolen capability is usable at all. |
| Single use and rotation | The number of commands one stolen capability can carry. |
| Binding to a permitted command set | The commands a stolen capability can carry. |
| Grant scope and path validation | What those commands can affect. |
| Operator approval for every mutating operation | Whether anything external changes. |
| Audit and revocation | How quickly misuse is noticed and stopped. |

This is the "detection by design" principle (DP-04). No claim is made that misuse is prevented.

## 7. Caller identity

| Rule | Requirement |
|---|---|
| L-C1 | The caller identity of a request is the triple: the session capability, the exact link, and the body digest. Two requests with the same triple are the same caller attempt. |
| L-C2 | The caller identity is what the idempotency cache and the reuse detection compare. It is not derived from the network path. |
| L-C3 | A source IP address, a user agent, a TLS fingerprint or any other network fingerprint MUST be treated as a risk signal only, and MUST NOT be used as an authentication factor, a binding factor or a substitute for the caller identity (XGN-DEC-007). |
| L-C4 | A risk signal MUST NOT by itself cause a request to be refused or a session to be suspended. A risk signal MAY raise the alert level attached to a `LINK_REUSE` event, and MUST be recorded with it. |
| L-C5 | The reason for L-C3 is specific: fetch infrastructure is shared, addresses and user agents vary between legitimate requests from the same agent, and two different agents routinely share both. Treating them as identity produces both false suspensions and missed attacks. |

**L-C6.** The session capability, not the network path, identifies the session. A request that presents a valid capability of another session MUST NOT be attributed to the requesting session, and MUST NOT be attributed to the presenting network address.

## 8. Capability logging and redaction

| Rule | Requirement |
|---|---|
| L-G1 | The gateway MUST disable query-string logging for the navigation route where the platform allows it. This MUST be verified in configuration and in test, not assumed (XGN-20). |
| L-G2 | Where the platform does not allow query strings to be excluded, the gateway MUST redact the value of the `t` parameter before the request is written to any log, at the earliest point in the logging path. |
| L-G3 | A redacted capability MUST be replaced by a stable, non-reversible reference, `cap_ref`, derived as the first 8 hexadecimal characters of `HMAC(server_reference_key, capability_value)`. This permits correlation across log entries without disclosing the capability. |
| L-G4 | Log entries for this route MUST NOT record agent-written content, parameter values other than the redacted capability, request bodies or response bodies. |
| L-G5 | The server reference key MUST be separate from the capability generation key, MUST NOT be derived from any credential, and MUST be rotated on the schedule XGN-27 sets. |
| L-G6 | A capability that appears in a log is of low value once it has been consumed, because it is single-use and short-lived. A log that captures a live capability before it is used remains a residual risk: it allows one impersonated command inside the grant before detection. That risk MUST be recorded in XGN-24 and MUST be accepted by the operator before the route is deployed with logging enabled. |

## 9. Revocation

| Rule | Requirement |
|---|---|
| L-V1 | The operator MUST be able to revoke a session. Revocation is an operator-plane action and MUST NOT be reachable from the agent plane (INV-01). |
| L-V2 | Revocation MUST invalidate every outstanding capability of that session immediately, including the one in flight and any cached reply reference. |
| L-V3 | Revocation MUST move the session to a terminal state. A subsequent request MUST be refused as `SESSION_REVOKED`, with no further detail. |
| L-V4 | Revocation MUST purge the session's idempotency cache entries and any gateway-held registry entries for that session within 5 seconds. |
| L-V5 | Revocation MUST be recorded as an event, with the session, the operator, the time and the reason. It MUST NOT record a capability value. |
| L-V6 | Revocation MUST NOT affect any other session. Sessions are isolated from one another. |

## 10. Capability and replay requirements

| ID | Requirement |
|---|---|
| L-01 | A capability MUST be `cap_` followed by 22 base64url characters, carrying at least 128 bits of entropy from a cryptographically secure random source. |
| L-02 | A capability MUST be opaque. It MUST NOT encode the session, the node, the sequence number, the grant or the permitted commands. |
| L-03 | A capability MUST be bound to the session, the grant, the node, the expected next sequence number, and the permitted command and parameter names. |
| L-04 | The runtime MUST verify every element of the binding before acting on a request. |
| L-05 | The binding MUST be to command and parameter **names**, never to values. A capability permits a command in principle; it never permits a value in advance. |
| L-06 | A capability MUST be single-use and MUST be rotated on every command reply. |
| L-07 | A capability MUST be valid until used or for 10 minutes, whichever comes first. |
| L-08 | An exact retry inside the 90-second window MUST return the cached reply byte for byte and MUST produce no second effect. |
| L-09 | A retry MUST be byte-identical to be an exact retry. |
| L-10 | After the window, a retry MUST NOT be recoverable by the agent alone, and the agent's recovery is a read of authoritative state. |
| L-11 | Every presentation of a consumed or superseded capability MUST be recorded as `LINK_REUSE`. |
| L-12 | A reuse that is not an exact retry inside the window MUST suspend the session and alert the operator. |
| L-13 | The design MUST be stated as detecting use, not preventing the first use by an attacker. |
| L-14 | The caller identity MUST be the session capability, the exact link and the body digest. |
| L-15 | A network fingerprint MUST be a risk signal only and MUST NOT be used as an authentication factor. |
| L-16 | The gateway MUST disable query-string logging for this route where the platform allows it, and MUST redact the capability value where it does not. |
| L-17 | Revocation MUST invalidate every outstanding capability of the session immediately and MUST purge the idempotency cache. |
| L-18 | The gateway MUST NOT be authoritative for the capability registry; the runtime record wins every disagreement. |

## 11. Decisions recorded

| ID | Decision | Where it is stated |
|---|---|---|
| `XGN-DEC-004` | Capability length: at least 128 bits of entropy, 22 base64url characters. The length probe uses the production length. | Section 2. |
| `XGN-DEC-007` | Idempotency window and caller identity: 90 seconds. Caller identity is the session capability plus the exact link and body digest. A network fingerprint is a risk signal only, never authentication. | Sections 5 and 7. |
| `XGN-DEC-008` | Session and capability lifetime: a capability is valid until used or for 10 minutes, whichever comes first. | Section 4. |
| `XGN-DEC-017` | The bare capability base is inert. Opening it returns the current panel and consumes nothing. | Section 4. |
| `XGN-DEC-056` | Capability binding: the binding tuple is session, grant, node, expected next sequence number, and the permitted command and parameter names, summarised by a `binding_digest`. The binding is to names, never to values. The value itself carries no binding. | Sections 2 and 3. |

`XGN-DEC-027` (the gateway MUST NOT cache a content-bearing reply) is owned by XGN-20 and is relied on in L-R5.
