# XGN-14: XGN Navigation Panels and Commands

**Status:** Proposed | **Version:** 1.0 | **Date:** 27 November 2026
**Module ID:** XGN-14 | **Group:** C — Transport
**Owner:** Gitana Architecture
**Depends on:** XGN-01, XGN-02, XGN-03, XGN-09 | **Supersedes:** none
**Conformance:** XGN-26 | **Open decisions:** none outstanding at this level

**Normative language:** MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119.

## 1. Purpose and scope

This module defines the **XGN Panel**: the single agent-visible reply that describes the current state of a session, the task, the draft, the outcome of the last command, and the commands that are legal right now.

In scope: the five blocks and their content rules; the field labels of the `DRAFT` block; the content of the `COMMANDS` block; the convention by which agent-written and repository-derived content is marked as data; the rendering of the `FIX` template; the `WAIT` panel; the rules a panel obeys; and the requirement that the same content be expressible in every transport.

Out of scope: the command catalogue and parameter order (XGN-28), the `FIX` template content (XGN-28), the capability format and lifecycle (XGN-29), the transport-specific request and response surface (XGN-10), the capability description (XGN-03), the draft model (XGN-07), the threat model of untrusted content (XGN-24), and the operation catalogue (XGN-19).

## 2. The panel

A panel is plain UTF-8 text with exactly five blocks, in this order:

```text
STATE     DRAFT  step 2 of 3
TASK      [x] create_branch  [>] write_file  [ ] create_pull_request
DRAFT     op=write_file
  repo    acme/app                  fixed
  branch  agent/task-42             fixed
  path    set, 13 bytes
  message set, 9 bytes
  content open, 9 bytes, parts: 1
LAST      ok: append seq=7
COMMANDS  base = https://gitana.example/gitana/nav/v1/s?t=<capability>
  append   &cmd=append&field=content&enc=text&data=<text>&seq=8
  preview  &cmd=preview&seq=8
  cancel   &cmd=cancel&seq=8
  limit    data up to 140 characters
```

### 2.1 Structure rules

| ID | Rule |
|---|---|
| B-01 | A panel MUST contain exactly the five blocks `STATE`, `TASK`, `DRAFT`, `LAST`, `COMMANDS`, in that order. |
| B-02 | A block header is the block name in upper case, padded to 8 characters, followed by two spaces, followed by the first line of the block. Content therefore starts at column 11. |
| B-03 | A continuation line within a block is indented by two spaces. A `DRAFT` field line is two spaces, then the field name padded to 8 characters, then one space, then the field description. |
| B-04 | A block with nothing to show MUST still appear, with `-` as its content. |
| B-05 | A line MUST NOT exceed 120 characters. A line that would exceed it MUST be wrapped at the last complete token, with the continuation indented by two spaces. |
| B-06 | A panel MUST NOT exceed 8192 bytes (XGN-10 section 6). |
| B-07 | Every label in a panel MUST be generated by Gitana. **No label MUST be derived from repository content or from agent-written content.** |
| B-08 | A panel MUST NOT contain a complete command URL, and a template MUST NOT contain a capability value (XGN-10 P-08). |
| B-09 | A panel MUST NOT contain a credential, a provider token or a capability other than the one it delivers (INV-14). |
| B-10 | The `COMMANDS` block and the `commands[]` array of the capability description MUST agree for the current state (XGN-03 CD-04). |

## 3. The `STATE` block

| Element | Content |
|---|---|
| The state name | Exactly one of the surface nodes: `LOCKED`, `HUB`, `DRAFT`, `PREVIEW`, `APPROVAL`, `RESULT`, `WAIT` (XGN-03 section 3.1). |
| The step | The current step and the total, for example `step 2 of 3`. Omitted in `LOCKED`. |
| The channel tier | The channel tier in force, for example `tier C`. |
| An instruction | In `WAIT` only, on a continuation line labelled `INSTR`, the generated instruction to report in chat and wait (section 10). |

**B-11.** The state name MUST be the authoritative state of the session, never a cached one. A panel MUST NOT claim a state the runtime has not confirmed.

## 4. The `TASK` block

The ordered steps of the grant, with progress.

| Element | Rule |
|---|---|
| Step marker | `[x]` for a completed step, `[>`] for the current step, `[ ]` for a pending step, `[-]` for a step that failed. |
| Step name | The step name from the grant. The grant is operator-defined, so this is Gitana content and not repository content. |
| Order | Steps MUST appear in the order the grant defines them. |

**B-12.** The `TASK` block MUST come from the grant and MUST NOT be derived from repository content.

**B-13.** The `TASK` block MUST NOT reveal steps, scopes or operations outside the grant. A step that the grant does not permit MUST NOT appear.

## 5. The `DRAFT` block

The first line is `op=<operation>`, or `-` when no draft is open. Then one line per field of that operation.

| Label | Meaning | What the line shows |
|---|---|---|
| **FIXED** | The field is fixed by the grant. The agent MUST NOT write it. | The value, and the word `fixed`. The value is grant content, not repository content and not agent content. |
| **MISSING** | A required field the agent has not written. | The word `missing`, and the required flag. |
| **SET** | A field the agent has written and which is complete. | The byte size, and the digest of the current value. |
| **OPEN** | A long field that has at least one part and may still receive more. | The byte size, the number of parts, and the digest of the value so far. |

| ID | Rule |
|---|---|
| B-14 | A field MUST be labelled with exactly one of FIXED, MISSING, SET or OPEN. The label MUST be the last token on the line. |
| B-15 | A SET or OPEN field MUST show its size in bytes and the first 32 hexadecimal characters of the SHA-256 digest of its canonical value, prefixed `sha256:` (XGN-DEC-003). |
| B-16 | A SET or OPEN field MUST NOT show the agent-written value. The value appears only in an explicit read (INV-13). |
| B-17 | `parts: <n>` is the **count** of parts in the field. Where part identifiers are shown, they MUST be labelled `part ids:` and listed in ascending order. The inherited label, which was ambiguous between a count and an identifier, is corrected here. |
| B-18 | A FIXED field MUST NOT be offered for writing by the `COMMANDS` block, and a `set` on it MUST be refused (XGN-28 Q-M1). |
| B-19 | The size shown MUST be the size of the decoded value. |
| B-20 | A field the operation does not declare MUST NOT appear, and a field that the grant does not permit MUST NOT appear. |

## 6. The `LAST` block

The outcome of the previous command.

| Outcome | Content |
|---|---|
| Accepted | `ok: <command> seq=<n>`. |
| Refused | `rejected: <ERROR_CODE>`, followed by the `FIX` template (section 9). |
| No command yet | `-`. |

| ID | Rule |
|---|---|
| B-21 | The outcome MUST describe the previous command, not the session as a whole. |
| B-22 | The outcome MUST NOT contain a capability value, a credential or agent-written content. |
| B-23 | The error code MUST be a stable code from the error catalogue (XGN-23). The remediation text MUST match the error contract's `remediation` for that code (XGN-03 CD-07). |
| B-24 | An error message MUST NOT include provider text verbatim and MUST NOT include the rejected value. |

## 7. The `COMMANDS` block

```text
COMMANDS  base = https://gitana.example/gitana/nav/v1/s?t=cap_<22 base64url characters>
  new      &cmd=new&op=<operation>&seq=8
  set      &cmd=set&field=<name>&value=<value>&seq=8
  append   &cmd=append&field=<name>&enc=text&data=<text>&seq=8
  replace  &cmd=replace&part=<part>&enc=text&data=<text>&seq=8
  unset    &cmd=unset&field=<name>&seq=8
  batch    &cmd=batch&ops=<ops>&seq=8
  preview  &cmd=preview&seq=8
  show     &cmd=show&field=<name>&page=<n>&seq=8
  commit   &cmd=commit&hash=<draft digest>&seq=8
  cancel   &cmd=cancel&seq=8
  status   &cmd=status
  limit    data up to 140 characters
  url      up to 900 characters
```

| Element | Rule |
|---|---|
| The base | The current capability base. This is the only capability the panel carries. |
| The templates | One line per command that is legal in the current state, with the parameters of that command in the fixed order (XGN-28 section 3). |
| The sequence number | Every command template ends with the **next** session sequence number. `status` carries no sequence number, because it is a read. |
| The limits | The applicable encoded-data limit and the applicable URL length. |
| The commit digest | In `PREVIEW`, the `commit` template carries the draft digest returned by the last `preview`. |

| ID | Rule |
|---|---|
| B-25 | Only commands legal in the current state MUST be listed (INV-12). A command not legal MUST NOT appear, even as an example. |
| B-26 | Every listed template MUST carry the same next sequence number, and that value MUST be the one the runtime will accept. |
| B-27 | A template MUST NOT contain a capability value. Only the base line carries the capability. |
| B-28 | The applicable limits MUST be stated, with the numeric value. The value MUST be the limit the runtime enforces, not a nominal one (XGN-03 CD-05). |
| B-29 | The `COMMANDS` block MUST be present in every panel, including in `WAIT`, where it carries only the re-check template. |
| B-30 | A panel MUST NOT contain a template that would perform an operator-plane action. The agent plane has no operator verbs (XGN-00 section 4.2). |

## 8. Untrusted content presentation

Agent-written content and repository-derived content are the two channels by which a prompt injection can reach an operator or an agent. The panel is therefore the place where that boundary is enforced.

| ID | Rule |
|---|---|
| B-31 | Agent-written content and repository-derived content MUST appear only inside an explicit read, in a marked data region (INV-13). |
| B-32 | Outside a marked data region, such content MUST appear only as sizes and digests. |
| B-33 | A marked data region MUST be introduced by a header line of the form `DATA  <descriptor>` and terminated by the line `END   DATA`. The descriptor MUST name the source and MUST carry the exact byte count of the region: `DATA  field=content page=1 of 2 bytes=512`. |
| B-34 | Exactly the stated number of bytes MUST follow the header line, verbatim. The content MUST NOT be escaped, re-encoded, summarised or truncated. |
| B-35 | The byte count is what makes the region unambiguous: a reader consumes exactly that many bytes, whatever they contain. A line inside the region that looks like a block label, a `DATA` header or an `END   DATA` terminator is content, and MUST NOT be interpreted as structure. |
| B-36 | The runtime MUST NOT interpret anything inside a marked data region as an instruction, and MUST NOT generate a label, a command, a URL, a state change or an operator message from it. |
| B-37 | A marked data region MUST NOT contain a capability value, even if the agent wrote one. |
| B-38 | The runtime MUST NOT cache a reply that contains a marked data region (XGN-DEC-027). |

**Example.**

```text
DRAFT     op=write_file
  repo    acme/app                  fixed
  path    set, 13 bytes
DATA  field=content page=1 of 2 bytes=512
<512 bytes of the agent's own content>
END   DATA
LAST      ok: show field=content page=1 of 2
```

**Where the control belongs.** The rule that content is data and not instructions is a security property owned by XGN-24, and the operator-plane separation is owned by XGN-00 and XGN-16. This module owns only the marking convention, so that every transport marks content the same way.

## 9. The `FIX` template

When the previous command was refused, the `LAST` block MUST contain the `FIX` template defined by XGN-28 section 6.

| ID | Rule |
|---|---|
| B-39 | The `FIX` template MUST be present when the last command was refused, and MUST NOT be present otherwise. |
| B-40 | Each element of the template MUST be on its own continuation line, indented by two spaces, in the order XGN-28 defines: `code`, `field`, `cause`, `current`, `allowed`, `retry`. |
| B-41 | The template MUST NOT contain a capability value and MUST NOT contain a link. |
| B-42 | The `current` element MUST show a state description, never a value. |

## 10. The `WAIT` panel

The `WAIT` node is offered when a turn gate is unreached, the session is suspended, the outcome of a request is unknown, or the device is unreachable (XGN-03 section 3.1).

| ID | Rule |
|---|---|
| B-43 | The `WAIT` panel MUST contain no forward link and no command template other than the rate-limited re-check. |
| B-44 | The `COMMANDS` block MUST carry exactly one template, the `status` re-check, with no sequence number. |
| B-45 | The `STATE` block MUST carry an `INSTR` continuation line with the generated instruction to report in chat and wait. The instruction MUST NOT contain a link and MUST NOT be a claim that anything was authorised. |
| B-46 | The re-check interval MUST be stated: the minimum interval between polls, and the number of polls allowed per session (XGN-10 section 6). |
| B-47 | The `LAST` block MUST state why the session is waiting, using a stable reason code and no content. |
| B-48 | Polling beyond the allowance MUST be refused as `RATE_LIMITED`. Excessive polling MAY suspend the session (XGN-23). |

## 11. Panel rules

| ID | Rule |
|---|---|
| B-49 | A panel MUST offer only commands that are legal in the current state. |
| B-50 | A refused command MUST leave the draft, the pending request and the next sequence number unchanged, and the reply MUST carry a fresh capability (INV-11, XGN-DEC-024). |
| B-51 | The next sequence number stated in the panel MUST be the value the runtime will accept next. |
| B-52 | A panel MUST NOT assert that an operation was accepted or executed unless the runtime has confirmed it (XGN-00 section 5). |
| B-53 | A panel MUST be reproducible: the same session state MUST produce the same panel, except for the capability value and the reply timestamp. |
| B-54 | A panel MUST NOT contain content from another session, another draft, or another operator. |
| B-55 | An agent MUST be able to continue from the panel alone. Where the panel is insufficient to continue, that is a defect in the panel, not in the agent. |

## 12. Cross-transport equivalence

The content of a panel is transport-independent. Only the rendering of the command URL differs.

| ID | Rule |
|---|---|
| B-56 | Every transport MUST express the same five blocks, the same field labels, the same command set, the same limits and the same error codes. |
| B-57 | A transport MUST NOT summarise, translate, reorder, abbreviate or omit a block. A transport that cannot carry a block MUST state which block it cannot carry, and MUST NOT alter the others. |
| B-58 | A transport MUST NOT ship a static or shortened copy of the panel content. It MUST be generated from the same authoritative definitions the validator uses (XGN-03 CD-01). |

**Transport-specific rendering rules.**

| Transport | Rendering |
|---|---|
| Composed GET (XGN-10) | Plain UTF-8 text as above. The command is expressed as a query suffix on the capability base. |
| Connector and tool (XGN-11) | A structured result whose `panel` field holds the same five blocks verbatim, with the machine-readable `commands[]` array alongside it. |
| Shell and authenticated (XGN-12) | The same five blocks printed verbatim by the navigation command, with the command expressed as a named subcommand and its parameters. |
| Copy/paste handoff (XGN-13) | The same five blocks inside the handoff package the operator pastes. |

The URL form of a command is a Composed GET concern. Other transports express the same command by name and parameters. The mapping is owned by XGN-09.

## 13. Panel requirements

| ID | Requirement |
|---|---|
| B-01 | A panel MUST contain exactly the five blocks `STATE`, `TASK`, `DRAFT`, `LAST`, `COMMANDS`, in that order. |
| B-02 | Every label MUST be generated by Gitana and MUST NOT be derived from repository or agent content. |
| B-03 | The `DRAFT` block MUST label each field FIXED, MISSING, SET or OPEN, with sizes and digests, and MUST NOT show agent-written values. |
| B-04 | The `COMMANDS` block MUST carry the capability base, the legal command templates, the next sequence number and the applicable size limit. |
| B-05 | The panel MUST offer only commands legal in the current state. |
| B-06 | A refused command MUST leave the draft and the next sequence number unchanged, and the reply MUST carry a fresh capability. |
| B-07 | Agent-written and repository-derived content MUST appear only inside an explicit read, in a marked data region with an explicit byte count. |
| B-08 | The runtime MUST NOT interpret content inside a marked data region as an instruction. |
| B-09 | A reply that contains a marked data region MUST NOT be cached. |
| B-10 | The `FIX` template MUST be present after a refused command, MUST be absent otherwise, and MUST NOT contain a capability or a link. |
| B-11 | The `WAIT` panel MUST offer only a rate-limited re-check and MUST instruct the agent to report in chat and wait. |
| B-12 | Every transport MUST express the same panel content and MUST NOT ship a static copy. |
| B-13 | A panel MUST NOT contain a complete command URL, a credential, or a capability other than the one it delivers. |
| B-14 | A panel MUST NOT assert that an operation was accepted or executed unless the runtime has confirmed it. |
