# XGN-16: XGN Approval and Operator Control

**Status:** Proposed | **Version:** 1.0 | **Date:** 27 November 2026
**Module ID:** XGN-16 | **Group:** D — Policy, approval, and execution
**Owner:** Gitana Architecture
**Depends on:** XGN-02, XGN-05, XGN-15, XGN-17, XGN-24, XGN-25, XGN-31 | **Supersedes:** none
**Conformance:** XGN-26 | **Open decisions:** A-OD-01, A-OD-02 (section 1.3)

**Normative language:** MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119.

## 1. Purpose and scope

### 1.1 Purpose

This module defines the operator's control surface: the approval screen the operator reads, the evidence an approval produces, the requirement for approval, the semantics of approve and decline, approval expiry, the actions that exist only on the operator plane, the management of approval frequency, the notifications the operator receives, and the treatment of untrusted content inside the approval surface.

Approval records the operator's decision. It does not decide whether an operation is permitted; policy does that, and is owned by XGN-15. It does not execute anything; dispatch is owned by XGN-17.

### 1.2 In scope and out of scope

| In scope | Out of scope |
|---|---|
| The approval screen layout and its content rules | The policy decision and the check set — XGN-15 |
| The approval record and its binding to the request | The dispatch, the credential custody and the execution record — XGN-17 |
| When approval is required, and approve and decline semantics | The operator-plane identity model and the pairing challenge — XGN-05 |
| Approval expiry, budgets, turn gates and notification | The panel format shown to the agent — XGN-14 |
| The boundary between operator content and agent content | The full threat model and the data-retention rules — XGN-24, XGN-25 |

### 1.3 Open decisions

| ID | Question | Interim position |
|---|---|---|
| A-OD-01 | Whether a decline reason may be surfaced to the agent | Not by default. If surfaced, it is a marked data field of at most 280 characters. |
| A-OD-02 | Whether the approval budget is counted per session, per step or per hour | Per session and per step. A per-hour budget is not defined until a use case is stated. |

## 2. The approval screen

### 2.1 The screen is a review, not a consent dialog

| ID | Requirement |
|---|---|
| A-01 | The approval screen MUST present the request as a code review. A generic consent dialog that asks only whether to allow an action is prohibited. |
| A-02 | The screen MUST use a fixed block layout. The blocks below are always present, in this order, for every operation. |
| A-03 | Every label on the screen MUST be generated by Gitana from the envelope and the provider state. No label, heading or button text may be derived from agent-written content or repository content. |
| A-04 | The screen MUST NOT contain a capability, a link, a token or any other agent-reachable action (INV-01, XGN-24). |
| A-05 | The screen MUST be renderable without the agent's content. Where the renderer cannot guarantee the delimiting required by section 8, it MUST show only sizes and digests. |

### 2.2 The block layout

```text
Gitana — Request approval
Awaiting approval

OPERATION
  Write file
  Request req_7Qm2x0Zr4n8Vc1aBd6Ef
  Step 2 of 3

TARGET
  Repository   acme/app
  Branch       agent/task-42
  Base branch  main
  Path         docs/notes.md

CHANGE SUMMARY
  + 12 lines
  - 3 lines
  1,284 bytes of content
  Request digest        9c1e4b7d2a8f0c3e5b6a7d8f9e0c1b2a
  Expected file digest  e69de29bb2d1d6434b8b29ae775ad8c2e48c5391
  Expected branch head  3c4f5e6a7b8c9d0e1f2a3b4c5d6e7f8091a2b3c4

PULL REQUEST
  Title        Add release notes
  Base         main
  Head         agent/task-42
  Body         2 paragraphs, 310 bytes

OVERWRITE
  This path already exists. Its current content will be replaced.

SECURITY VERIFICATION
  Repository scope        Valid
  Branch permissions      Valid
  Request integrity       Verified
  Operator authorisation  Required

ACTIONS
  Approve      Decline
```

### 2.3 Block rules

| ID | Block | Requirement |
|---|---|---|
| A-06 | `OPERATION` | MUST name the operation in plain words, the request identifier and the step. |
| A-07 | `TARGET` | MUST name the repository, the branch, the base branch and the path. For a pull request the head and the base are also shown in `PULL REQUEST`. |
| A-08 | `CHANGE SUMMARY` | MUST state the number of added lines and the number of removed lines, the content size in bytes, the request digest as exactly the 32 exposed hexadecimal characters the execution layer will verify at dispatch, the expected file digest and the expected branch head (XGN-31 I-33, I-34). For a new file, added lines is the line count of the content and removed lines is 0. For a pull request, the summary counts the changes the pull request proposes. |
| A-09 | `PULL REQUEST` | MUST state the title, the base branch and the head branch, and the size of the body. The body text itself is rendered as data under section 8. |
| A-10 | `OVERWRITE` | MUST be present for every operation. When the operation replaces existing content, it MUST carry an explicit overwrite warning naming the path. When it does not, the block states that no existing content is replaced. |
| A-11 | `SECURITY VERIFICATION` | MUST carry the four lines below. Each line states a result, not an explanation. |
| A-12 | `ACTIONS` | MUST offer exactly two actions, Approve and Decline. It MUST NOT offer an action that is not defined in this module. |
| A-13 | `SECURITY VERIFICATION` MUST state `Repository scope Valid` only when the repository, branch and path passed the scope checks of XGN-15 at the point of presentation. | — |
| A-14 | `SECURITY VERIFICATION` MUST state `Branch permissions Valid` only when the provider has confirmed that the branch is writable under the credential in use, or is a read-only branch for a read operation. | — |
| A-15 | `SECURITY VERIFICATION` MUST state `Request integrity Verified` only when the envelope digest has been recomputed and matches the digest presented for approval. It MUST NOT be stated otherwise. | — |
| A-16 | `SECURITY VERIFICATION` MUST state `Operator authorisation Required` whenever the screen is shown. The line is the record that the operator's decision is the outstanding authorisation. | — |

### 2.4 Content size and expansion

| ID | Requirement |
|---|---|
| A-17 | Content of 4096 bytes or less MAY be shown in full inside the data region. Content above 4096 bytes MUST be summarised with its size and digest, and MUST NOT be rendered inline. |
| A-18 | The operator MAY expand the content on the trusted device. Expansion is an operator-plane action and MUST NOT be reachable from the agent plane. |
| A-19 | The summary MUST be computed by the runtime from the envelope and the provider state. The agent MUST NOT supply the summary, the line counts, the size or the digest. |
| A-20 | A line count MUST be computed against the expected base content named by the operation's preconditions. Where no base content exists, the count MUST be the line count of the submitted content. |

## 3. Approval evidence

### 3.1 The approval record

The schema is owned by XGN-02 section 7. This module fixes what each field must contain and what binds the approval.

| Field | Requirement |
|---|---|
| `approval_id` | Identifies the decision. Unique, never reused (XGN-01 section 4). |
| `request_id` | The request the decision applies to. |
| `envelope_digest` | The digest of the complete immutable envelope that was presented. An approval without a digest is invalid. |
| `decision` | `APPROVE` or `DECLINE`. |
| `decided_by` | The operator principal. Never an agent, never a chat message. |
| `decided_at` | Stamped by the runtime. |
| `expires_at` | Stamped by the runtime, 10 minutes after presentation (section 6). |
| `summary_digest` | The digest of the approval summary that was displayed, so that the record proves what the operator actually saw. |
| `signature` | The runtime signature over the canonical representation of the envelope (XGN-31 I-22 to I-25). It is carried by the approval, not by the envelope. |
| `signing_key_id` | The identifier of the device key that produced the signature, so that the signature can be verified at dispatch. |

| ID | Requirement |
|---|---|
The binding rules themselves are owned by XGN-31 section 5. This module fixes what the approval service does with them.

| A-21 | The approval MUST bind to the `envelope_digest` of the presented envelope, and an approval without a digest is invalid (XGN-31 I-16). |
| A-22 | The envelope digest MUST cover the complete immutable envelope, including the expected provider state such as the expected blob digest and the expected head digest (XGN-DEC-019, XGN-31 I-07). |
| A-23 | Any material change to the request after the approval invalidates the approval. A material change is any change to the envelope: the operation, the arguments, the normalised path, the parts, the step, the scope, the expiry or the part order (XGN-31 I-19, I-20). |
| A-24 | After a material change, the runtime MUST refuse to dispatch under the existing approval, with `INTEGRITY_MISMATCH`. It MUST NOT re-dispatch under the old digest. |
| A-25 | The approval MUST NOT be transferable to another request, another session, another step or another envelope. |
| A-26 | The approval record MUST be retained as audit evidence even when the request is declined, expired or superseded (XGN-25). |
| A-27 | A change in the **provider state** after the approval does not invalidate the approval record. The record remains bound to the digest it approved; the dispatch is refused against the current state and the agent re-previews and re-commits (XGN-31 I-28 to I-31). |

### 3.2 Binding to the dispatched request

| ID | Requirement |
|---|---|
| A-28 | The approved request MUST be the dispatched request, byte for byte (INV-06). |
| A-29 | The runtime MUST recompute the envelope digest at dispatch and compare it with the digest in the approval record. A mismatch MUST abort the dispatch (XGN-17). |
| A-30 | The operator is notified whenever an approval is invalidated by a material change, so that the operator's belief about what was approved is never stale. |

## 4. When approval is required

| ID | Requirement |
|---|---|
| A-31 | Every mutating commit MUST require an operator approval, on every transport, without exception (XGN-DEC-006). |
| A-32 | This requirement applies to `create_branch`, `write_file`, `create_pull_request`, and `delete_file` where it is enabled. A pull request is a mutation of the repository's collaboration state and is not exempt. |
| A-33 | Clearing a turn gate MUST NOT satisfy the approval requirement of a mutating operation (XGN-DEC-011). A cleared turn and an approval are separate records, and both are retained. |
| A-34 | A read operation does not require approval unless policy raises the requirement. The operator MAY raise it (XGN-15 section 4). |
| A-35 | The approval requirement MUST NOT be satisfied by any agent-plane action, by a chat message, by a prior approval of a similar request, or by the absence of objection (INV-01, INV-02). |

## 5. Approve and decline

### 5.1 Approve

| ID | Requirement |
|---|---|
| A-36 | An approval authorises exactly one dispatch of the envelope whose digest it carries. |
| A-37 | The runtime MUST dispatch the approved envelope and no other. The dispatched arguments MUST equal the presented arguments. |
| A-38 | The dispatch remains subject to the pre-dispatch checklist of XGN-17, including the policy re-evaluation immediately before dispatch. An approval does not skip it. |
| A-39 | The approval MUST NOT be reused after the request has been dispatched, declined or closed. |

### 5.2 Decline

| ID | Requirement |
|---|---|
| A-40 | A decline closes the request. The request MUST NOT be dispatched afterwards, including by a retry of the same command. |
| A-41 | The session MUST return to the hub at the same step. The step is retained: the step is not marked complete, and the agent may open a new draft for it. |
| A-42 | The agent MUST be told that the step is unchanged, through a panel whose `LAST` block states the outcome and a stable error code. The agent MUST NOT be told that the operation was refused for a reason it could fix by guessing. |
| A-43 | The declined request MUST remain in the audit log with its envelope digest and the decline reason code. It MUST NOT be redispatched. |
| A-44 | A decline reason MAY be recorded by the operator. A reason MUST NOT carry a capability, a credential or an operator-plane action. |

### 5.3 What the agent may do after a decline

| ID | Requirement |
|---|---|
| A-45 | The agent MAY open a new draft and commit again. A new commit produces a new envelope, a new digest and a new approval. The declined request remains declined. |
| A-46 | The agent MUST NOT be able to re-present the declined envelope unchanged as if it were new. It MAY do so only as an explicit re-commit, which is a new request with a new identifier. |

## 6. Approval expiry

| ID | Requirement |
|---|---|
| A-47 | An approval is valid for 10 minutes from the moment it was presented to the operator (XGN-DEC-043). The runtime stamps `expires_at` accordingly. |
| A-48 | An expired approval MUST NOT authorise dispatch. The runtime MUST refuse the dispatch and MUST record the refusal. |
| A-49 | A request whose approval has expired returns to a state that requires a fresh commit. The request is closed as expired; the envelope is retained as audit evidence and is not dispatchable. |
| A-50 | The expiry MUST be re-checked at the moment of dispatch, not only when the approval was recorded (XGN-17). |
| A-51 | An expired approval MUST NOT be renewed. A fresh commit produces a fresh envelope, a fresh digest and a fresh approval. |
| A-52 | The operator MAY decline an approval at any time before dispatch, including after approving it, to withdraw the authorisation before the operation takes effect. A decline after approval MUST prevent the dispatch and MUST be recorded as a distinct event. |

## 7. Operator-only actions

| ID | Action | Plane |
|---|---|---|
| A-53 | Create a session and its grant | Operator only |
| A-54 | Confirm the pairing challenge | Operator only |
| A-55 | Clear a turn gate or set a gate | Operator only |
| A-56 | Approve or decline a request | Operator only |
| A-57 | Narrow the policy or the scope configuration | Operator only |
| A-58 | Suspend, resume, revoke or extend a session | Operator only |
| A-59 | Rotate or revoke a provider credential | Operator only |
| A-60 | Expand or inspect content, and read the audit log | Operator only |
| A-61 | Change the transport or the channel tier opt-in | Operator only |

| ID | Requirement |
|---|---|
| A-62 | None of the actions in this section may be reachable from the agent plane (INV-01). No agent-plane reply may contain a link, token, parameter or instruction that performs any of them. |
| A-63 | The agent plane MUST NOT carry verbs for these actions. A command naming one MUST be rejected as an unknown command. |
| A-64 | A conversation between an agent and an operator never authorises anything. A message may inform an operator and may never substitute for an operator-plane action (INV-02). |
| A-65 | Operator-plane authentication MUST be independent of every agent-plane credential (XGN-05). |

## 8. Untrusted content in the approval screen

The approval surface is a trust boundary between the operator and content the agent wrote or read from the repository. The rules of XGN-24 section 6 and H-19 apply here, and the rules below make them concrete for this surface.

| ID | Requirement |
|---|---|
| A-66 | Agent-written content and repository-derived content are untrusted. They MUST be rendered as data and MUST NOT be rendered as instruction. |
| A-67 | Untrusted content MUST be confined to a delimited data region whose header states that the region contains untrusted data supplied by the agent or read from the repository. |
| A-68 | The runtime MUST NOT interpret agent-written content as an instruction, and MUST NOT act on content that asks for anything. A request inside content, including one asking for an approval, has no effect. |
| A-69 | Untrusted content MUST be escaped so that markup, links, code fences and terminal escape sequences cannot render as an action, a button or a terminal control. |
| A-70 | The data region delimiter MUST NOT be escapable by the content. An occurrence of the delimiter inside the content MUST be escaped before rendering. |
| A-71 | A pull request title and a pull request body are agent-written content and MUST be rendered under this rule, including when they are displayed as a summary. |
| A-72 | The security verification lines, the operation name, the target block and the change summary are generated from the envelope and MUST NOT contain agent text, except that the change summary counts the agent's lines. |
| A-73 | The approval screen MUST NOT contain repository content outside an explicit read, and MUST NOT contain a provider response body (XGN-24). |

## 9. Approval frequency

### 9.1 Budgets

| ID | Requirement |
|---|---|
| A-74 | The runtime MUST enforce an approval budget of 20 approvals per session and 5 approvals per step. |
| A-75 | Reaching a budget MUST stop further approval prompts. The session moves to a waiting state and the operator is notified. |
| A-76 | A budget MUST NOT lower the approval floor in XGN-15 section 4.1. When the budget is exhausted, a mutating operation is not dispatched without approval; it waits for the operator. |
| A-77 | The budget MUST be visible to the operator and MUST be stated in the capability description (XGN-03). |

### 9.2 Turn gates

| ID | Requirement |
|---|---|
| A-78 | A turn gate MAY hold the session between steps so that several steps are reviewed before the agent continues. A gate reduces interruptions; it does not reduce the approval requirement of a mutating operation. |
| A-79 | Clearing a gate MUST NOT be recorded as an approval, and an approval MUST NOT be recorded as a cleared gate (XGN-DEC-011). |

### 9.3 Operator adjustment

| ID | Requirement |
|---|---|
| A-80 | The operator MAY narrow what requires approval, by raising the requirement for read operations, by shortening the approval expiry below 10 minutes, or by disabling an operation class. |
| A-81 | The operator MAY widen what is interrupted, by reducing notifications for read operations or by grouping gates. A widening MUST NOT reduce a mutating operation below the approval floor. |
| A-82 | An operator configuration that would reduce a mutating operation below the approval floor MUST be rejected, and the previous configuration MUST remain in force (XGN-15 section 4.1). |

## 10. Notifications

| ID | Requirement |
|---|---|
| A-83 | The operator MUST be notified when an approval is required, when a session is suspended, and when an outcome is unknown. |
| A-84 | A notification MUST name the request, the session, the operation, the state and the action required, and MUST NOT contain a capability or a link that performs the action. The action is taken on the trusted device. |
| A-85 | A notification MUST NOT contain agent-written content, repository content, a credential, a capability or any part of a URL that carries one (INV-13, INV-14). It MAY contain identifiers, operation names, repository and branch names, paths, sizes, counts and digests. |
| A-86 | A notification MUST NOT contain a provider response body or a provider error message verbatim. |
| A-87 | A notification about an unknown outcome MUST state that the outcome is unresolved and that no further operation will be attempted without the operator's instruction. |
| A-88 | A notification MAY state that a declined request is still retained as evidence. It MUST NOT invite the agent to repeat the request. |
