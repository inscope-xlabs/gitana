# XGN-05: XGN Identity and Trust Model

**Status:** Proposed | **Version:** 1.0 | **Date:** 27 November 2026
**Module ID:** XGN-05 | **Group:** B — Session and request lifecycle
**Owner:** Gitana Architecture
**Depends on:** XGN-01, XGN-02, XGN-03 | **Supersedes:** none
**Conformance:** XGN-26 | **Open decisions:** see section 11

**Normative language:** MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119.

## 1. Purpose and scope

This module defines **who may act** in XGN, **how each party proves who it is**, and **where the trust boundaries lie**: the principals, the two control planes, the pairing challenge that replaces the inherited per-session secret, the credential classes and their lifecycle, and the rule that keeps a device fingerprint from being mistaken for an identity.

**Out of scope:** the command capability format and its replay rules (XGN-29), grant scope (XGN-04), approval capture and operator control (XGN-16), the threat model itself (XGN-24), the audit record and its retention (XGN-25), the gateway deployment (XGN-20) and the provider adapter (XGN-18).

## 2. Principals

A principal is an actor that XGN can attribute an action to. Every principal identifier is `prn_` plus 12 base64url characters, assigned by the trusted runtime (XGN-01 §4).

| Principal | What it is | What it authorises | Held by |
|---|---|---|---|
| **Operator** | The human on the trusted device. | Session creation, pairing confirmation, gate clearance, approval and decline, scope, suspension, resumption, revocation, credential management. | The device. |
| **Agent** | The AI agent or permitted client. | The agent plane only: reading panels, composing a draft, issuing commands that the grant permits. | The agent, which holds nothing but the current command capability. |
| **Gateway** | The XGN ingress component (XGN-20). | Nothing. It forwards, rate-limits, bounds size and routes. | The gateway infrastructure. |
| **Runtime** | The trusted Gitana runtime on the device (XGN-17). | The authoritative side of every cross-component contract: session, grant, draft, request, policy, approval, execution, audit. | The device. |
| **Provider** | The external service the runtime acts against (XGN-18). | Nothing on the agent's behalf. It applies only what the runtime dispatched. | The external service. |

| ID | Requirement |
|---|---|
| T-01 | A principal identifier MUST NOT encode a secret, a credential, a network location or a device fingerprint. |
| T-02 | The gateway MUST NOT be recorded as the principal of an operation. It forwards; it does not act (XGN-00 §5). |
| T-03 | The agent MUST NOT be recorded as the principal of an operator-plane action, and the operator MUST NOT be recorded as the principal of an agent command. |
| T-04 | A principal MUST NOT be inferred from a network or device fingerprint (section 8). |
| T-05 | Every audit event MUST name the acting principal and its kind, using the actor kinds of the Event Contract (XGN-02 §9). |

## 3. The two planes

XGN recognises exactly two control planes (XGN-00 §4.2).

| Plane | Controller | May do |
|---|---|---|
| **Agent plane** | The agent or permitted client | Read the capability description, read panels and status, open and edit a draft, commit a request, read the outcome. |
| **Operator plane** | The operator on the trusted device | Create sessions and grants, confirm pairing, clear gates and turns, approve or decline, extend or revoke, suspend and resume, manage policy and credentials. |

| ID | Requirement |
|---|---|
| T-06 | No agent-plane response may contain a link, token, parameter or instruction that performs an operator-plane action (INV-01). |
| T-07 | A conversation between an agent and an operator is outside the system. A chat message, a transcript, a pasted code or an agent-relayed instruction MUST NOT authorise anything and MUST NOT be accepted by any component as an operator action (INV-02). It MAY inform an operator and MAY prompt a device action; it MUST NOT substitute for that action, and the runtime MUST NOT record it as one. |
| T-09 | The agent-visible surface MUST offer only agent-plane commands. The runtime MUST NOT expose an operator verb, an operator route or an operator hint in a panel (XGN-14). |
| T-10 | Operator-plane authentication MUST be independent of every agent-plane credential (XGN-00 §4.2, section 5). |

## 4. Pairing challenge

A session is live only after the operator confirms pairing on the device. The mechanism is a **pairing challenge**: a non-secret one-time code of six digits, generated per session, shown on the device only (XGN-DEC-009). It replaces the inherited per-session secret, whose retired label is recorded in XGN-01 §2.1.

| ID | Requirement |
|---|---|
| T-11 | The pairing challenge MUST be six digits, MUST be generated by the runtime from a cryptographically secure source, and MUST be shown on the trusted device only. |
| T-12 | The pairing challenge MUST NOT appear in any agent-visible panel, reply, link, log or error, and MUST NOT be transmitted to the agent plane by any route. |
| T-13 | The pairing challenge MUST NOT be accepted by any component as an authorisation factor, a credential or a substitute for the operator credential. The server MUST NOT expose a route that accepts it. |
| T-14 | The session MUST remain in `LOCKED` until the operator confirms pairing on the device (XGN-04 §5). The agent MUST NOT be able to leave `LOCKED` (INV-01). |
| T-15 | The pairing confirmation MUST be authenticated by the operator credential, MUST be recorded as an audit event with the session identifier and the timestamp, and MUST be re-issued when the session is re-established after a runtime restart (XGN-DEC-028). |

**The ceremony.** (1) The runtime generates the pairing challenge for the session and displays it on the device. (2) The operator hands the session link to the agent out of band; the challenge is not part of the link. (3) The agent opens the link and receives the onboarding text, the capability description and a statement that pairing is pending on the operator's device — no code. (4) The operator confirms pairing on the device, and the session moves from `LOCKED` to `ACTIVE`. (5) The runtime records the confirmation and the agent continues.

The challenge identifies the pairing ceremony to the operator, so that an operator juggling several sessions can tell which one the conversation refers to. Because it is not a secret, the operator may read it aloud, show it on screen or let a camera see it. Doing so grants nothing: the authority to unlock the session is the operator's device-side confirmation, authenticated by the operator credential.

### 4.1 Why the inherited design is rejected

The inherited proposal required the agent to open the session link, read the per-session secret from a panel, report it in the chat application, and stop. The operator then compared the chat copy with the phone copy before confirming. That design is rejected, for five reasons.

1. **It moved a secret outside the trust boundary.** The boundary is the trusted device; the secret travelled into the chat application and the model's context, both outside Gitana's control. The agent is untrusted and the operator is the only authority (XGN-01); a secret held by the untrusted party cannot be an authority check.
2. **It added no independent entropy.** The secret was delivered by the session link itself. Anyone with a stolen or replayed link could read the panel, learn the secret and have it "confirmed". The unlocking factor was worth exactly as much as the link, so the ceremony bought no protection against the theft it appeared to address (XGN-00 AR-01; the inherited review recorded this as credential-in-URL exposure).
3. **It built a social-engineering script.** The ritual teaches the operator to receive a code from an agent and act on it. An attacker who can speak as the agent inherits that script, and the operator's reading of the code aloud becomes the unlock. A mechanism meant to establish trust became its most efficient abuse channel.
4. **It confused correlation with authorisation.** Comparing two copies of a code is a correlation step, yet the design presented the code as the thing that gated the session. In XGN the gate is the operator's credential on the device (T-10, T-13).
5. **It was unnecessary.** The only real purpose, binding a chat conversation to the right device session, is achieved by a non-secret device-only code plus a device-side confirmation, with nothing to leak.

**What replaces it.** The device displays a six-digit non-secret challenge; the agent never receives it; the operator confirms on the device; the unlock is authenticated by the operator credential. Possession of the session link confers no ability to unlock the session, and no code the agent may see or be told grants anything. The audit trail records that a confirmation happened, by which principal and when, not the code.

## 5. Credential classes

| Class | Holder | Purpose | Form and lifetime | Where it may appear |
|---|---|---|---|---|
| **Session capability** | The agent, in transit | Authorises one command inside one session (XGN-29). | `cap_` plus 22 base64url characters, 128 bits; single use; valid until used or 10 minutes. | The query of a transport link, nowhere else. |
| **Operator credential** | The trusted device only | Authenticates every operator-plane action (T-10). | A device-held key, or a key unwrapped by a device-local factor. No transport form exists. | Nowhere outside the device. |
| **Provider credential** | The trusted runtime only | Authenticates the runtime to the external service (XGN-18). | Long-lived, fine-grained, restricted to the approved repositories. | The runtime's outbound call to the provider adapter, nowhere else. |
| **Gateway device credential** | The gateway and the runtime | Authenticates the two components at the transport hop. | Per-installation, issued at enrolment. | The gateway-to-runtime hop only. |

| ID | Requirement |
|---|---|
| T-16 | No credential class may be derived from, or substituted by, another. The operator credential MUST NOT be derived from or replaceable by a session capability; the provider credential MUST NOT be derived from either; the gateway device credential MUST NOT confer operator authority. |
| T-17 | The operator credential MUST be independent of every agent-plane credential. Operator-plane authentication MUST NOT succeed or fail because an agent credential has expired, rotated or been revoked, and MUST NOT be derivable from anything the agent can observe. |
| T-18 | The provider credential MUST NOT leave the trusted runtime. It MUST NOT appear in a URL, a link, a reply, a panel, a log, an error message or an audit record (INV-14). |
| T-19 | A session capability MUST be scope-bound to one session and one grant, MUST be single use, and MUST be rotated on every response. The gateway MUST NOT mint, extend or re-scope a capability (XGN-29). |
| T-20 | A credential MUST NOT be used outside the boundary it was issued for. A gateway device credential MUST NOT authorise an operation, and a session capability MUST NOT perform an operator-plane action. |

## 6. Credential lifecycle

| Class | Issued by | Issued when | Rotated | Expires | Revoked by | After a runtime restart |
|---|---|---|---|---|---|---|
| Session capability | The gateway, on the runtime's authority | In every response carrying a forward command | Every response; the previous capability is invalidated at once | On use, or 10 minutes | Session revocation (XGN-04 §5.3), capability reuse detection (INV-09) | Not restored; a fresh capability is issued |
| Operator credential | The operator, at device enrolment | Device enrolment | On re-authentication or credential rotation (XGN-27) | Per device policy; the operator re-authenticates to unlock the device interface | The operator | Survives; the operator re-authenticates to act |
| Provider credential | The operator, in the external-service settings | Configuration | On provider rotation | Per provider policy | The operator, or the provider | Survives; it MUST be re-verified before the first dispatch after a restart |
| Gateway device credential | Enrolment | Installation or enrolment | On re-enrolment | Per installation policy | The operator | Survives if persisted; otherwise re-enrolment is required |

| ID | Requirement |
|---|---|
| T-21 | A credential MUST NOT be reused after its lifetime ends or after it is revoked. Revocation MUST be effective for every component that could present it. |
| T-22 | Rotation MUST NOT invalidate an already approved request. An approval binds to the request digest, not to a credential (XGN-31, XGN-16). |
| T-23 | After a runtime restart the operator credential and the provider credential MUST survive; session capability state MUST NOT. A request pending approval at restart is invalidated and requires a new commit (XGN-DEC-028, XGN-21). |
| T-24 | The runtime MUST re-verify the provider credential before the first dispatch after a restart, because a credential may have been revoked at the provider while the runtime was down. |

## 7. Trust boundaries

| Boundary | Who may cross | With what | What is forbidden |
|---|---|---|---|
| Agent ↔ chat application, fetch service | The agent and the application, which is outside Gitana's control | Ordinary URLs and replies. A command capability necessarily transits this channel. | Treating the application as a participant in authorisation. A reply, a fetch or a prefetch is not a policy decision, an approval or an execution. Content transiting this channel may be read by its provider (XGN-24). |
| Agent → XGN gateway | The agent | The current command capability, carrying one command. | Any operator verb; any attempt to set an identifier, a digest, a scope, a timestamp or a principal. |
| Gateway → trusted runtime | The gateway | The gateway device credential and the command capability. | Asserting a session state, a policy decision, an approval or an outcome (XGN-00 §5.1). |
| Runtime → operator | The runtime | Approval surfaces, notifications, and the operator's reply. | Deriving an approval summary from repository or agent content; presenting content as instruction (XGN-00 AR-08, XGN-16). |
| Operator → runtime | The operator, on the device | The operator credential. | Delegating an operator action to an agent-visible artefact, or accepting one relayed through chat (T-07). |
| Runtime → provider adapter → external service | The runtime | The provider credential, for an approved and dispatched request only. | Any request that was not approved and dispatched; the provider credential being readable by the agent (T-18). |
| Runtime → audit log | The runtime | Identifiers, digests, counters and reasons. | Content, secrets, capabilities, or provider text verbatim (INV-18, XGN-25). |
| Any component → agent-visible surface | The runtime, and the gateway when it relays a reply | Panels and links. | Another session's data, an operator-plane action, or content outside an explicit read (XGN-03 §2.2). |

| ID | Requirement |
|---|---|
| T-25 | The trusted runtime is the trust anchor. A component that is not the runtime MUST NOT be able to assert authority, and the device's record wins every disagreement about what was accepted or executed. |
| T-26 | Every cross-boundary communication MUST use the shared contracts of XGN-02. No undocumented direct dependency between components is permitted (INV-19). |

## 8. Device fingerprinting is a risk signal only

A device or network fingerprint — source address, user agent, header order, transport characteristics — is **not** an identity mechanism and MUST NOT be used as one.

| ID | Requirement |
|---|---|
| T-27 | A fingerprint MUST be treated as a risk signal only. It MAY raise a fork or replay suspicion, contribute to a risk score, trigger a step-up check or enrich an audit event. |
| T-28 | A fingerprint MUST NOT be used to authenticate an agent, to identify a principal, to decide that two requests come from the same session, to authorise an action, or to substitute for the operator credential. |
| T-29 | Caller identity for the idempotency window MUST be the session capability together with the exact link and body digest (XGN-DEC-007). |

**Why.** An agent owns no network location: it reaches Gitana through shared fetch infrastructure, proxies, chat applications and provider gateways, so one legitimate agent may appear from many addresses and one address may carry many agents. Fingerprints are also spoofable and unstable within a session. Treating one as identity converts a weak signal into an authorisation check, in the direction that matters most.

**What it is good for.** It is useful where a signal is wanted: an unexpected change of address or client between two commands inside one session is worth a suspicion score, an operator alert or a suspension. Detection by design is the point (XGN-00 DP-04).

## 9. Threat-relevant notes

The threat model is owned by XGN-24 and is not restated here. This module contributes to it as follows.

| Concern | Where it is treated |
|---|---|
| Capability theft, replay and link exposure | XGN-29; the analysis in XGN-24. |
| Social engineering of the operator | Section 4 removes the secret-relay ritual; the analysis in XGN-24. |
| Prompt injection from content into operator decisions | XGN-24 and XGN-00 AR-08; the runtime-generated approval summary in XGN-16. |
| Compromise of the gateway or the runtime | XGN-20 and XGN-24; the gateway holds no authoritative state (XGN-00 §5.1). |
| Provider credential compromise | XGN-18 and XGN-19; the credential never leaves the runtime (T-18). |

## 10. Decisions recorded

| ID | Decision | Owner |
|---|---|---|
| XGN-DEC-007 | Idempotency window 90 s; caller identity is the session capability plus the exact link and body digest; a network fingerprint is a risk signal only, never authentication. | XGN-29, applied in §8 |
| XGN-DEC-009 | The pairing challenge is a non-secret one-time code of six digits, shown on the device only; it never appears in an agent-visible panel and is never an authorisation factor. | XGN-05 |
| XGN-DEC-039 | Four credential classes: session capability, operator credential, provider credential, gateway device credential. None is derived from another, and the operator credential is independent of every agent-plane credential. | XGN-05 |
| XGN-DEC-049 | Pairing confirmation is device-local: the challenge never reaches the agent plane, no component accepts it as a credential, and the unlock is authenticated by the operator credential. | XGN-05 |

The register in XGN-01 §7 is the index; the owner module holds the authoritative statement.
